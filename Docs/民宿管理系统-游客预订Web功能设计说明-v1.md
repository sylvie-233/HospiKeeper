## 一、系统概述

### 1.1 定位

面向游客的**在线预订门户**（网页端），与民宿管理系统（桌面端）共用同一个 MySQL 数据库，实时联动房态：游客在线预订**锁定房型库存** → 桌面端预订单即时可见「待到店」→ 到店前台分配房间、一键转入住。

设计目标：游客**免登录、免支付**，三步完成预订（选日期 → 选房型 → 留手机号）；民宿侧零学习成本，预订自动进入既有业务闭环。

### 1.2 预订模型：房型预订，房间到店后分配（核心约定）

游客端**只订「房型 + 日期段」，全程不出现具体房间号**，这是酒店业的标准模式，本系统正式版遵循此模型：

1. **预订时**：只校验并扣减该房型的日期段库存，生成预订单（记录房型、入住/退房日期、客人信息），**不锁定任何具体房间**；
2. **到店日**：前台在桌面端「转入住」时，从该房型的空闲房中**分配具体房间**（系统可自动推荐房号，前台可改选），随后走既有入住流程；
3. **取消时**：只改预订单状态，无需释放任何房间，库存自动回补。

采用此模型的原因：

- **房态是动态的**：预订入住日的前一晚，具体某间房可能仍在打扫或被临时维修，提前锁死房号不灵活，还会让看板长期挂「预定」紫卡；
- **给酒店调度空间**：同房型多间房可统筹安排（团队集中楼层、长住客固定房间等）；
- **对齐行业标准**：携程/美团等 OTA 均为房型库存模型，将来对接渠道无需改造。

> **原型与正式版的差异说明**：`酒店管理系统-游客预订Web原型-v1.html` 为演示简化，预订提交时直接取一间空闲房置为「预定」并展示房号（演示效果直观）。**正式实现一律按本节模型执行**：预订单不落房号，成功页只展示「房型 + 日期」，桌面端转入住时才产生房号。

### 1.3 形态与风格

- **Web 门户形态**：顶部导航 + 首页（Hero 营销区）/ 客房预订 / 我的预订 三页，非后台布局；
- **控件风格**：延续桌面端 Ant Design 设计规范（主色 `#1677ff`、语义 Tag 色、圆角卡片、毛玻璃查询条），并针对 C 端加大字号与留白；
- **演示运行**：数据内置演示数据；正式版对应 MySQL 落库（见第六章数据规则与扩展建议）。

### 1.4 与桌面端的关系

| 事项 | 游客 Web 端 | 桌面端（前台/管理员） |
|------|------------|----------------------|
| 预订创建 | 游客自助，免登录，只锁房型库存（不指定房号） | 前台代客录入（可选填房号或到店再分配） |
| 房态变更 | **不直接变更房态**（预订不锁具体房间） | 全部六种房态流转；转入住时分配房间 → 已入住 |
| 预定单状态 | 待到店 / 已转入住 / 已取消 | 同一套状态，转入住（含选房）在桌面端操作 |
| 支付 | 不收款（到店支付） | 押金收取、退房结算 |

> 注意：正式版中游客预订**不再产生「空闲 → 预定」的房态变更**（原型简化版才有）；「预定」房态在桌面端语义改为「前台代客预订且已指定房号」的本地场景。

## 三、功能模块详细设计

### 3.1 首页（营销 + 快速入口）

- **Hero 区**：品牌标语、位置卖点、统计条（14 客房 / 3 房型 / 5min 步行至湖边 / 4.9 评分），数据为演示数据；
- **快速查询条**：入住日期（默认今天，最早今天）、退房日期（默认明天，最早明天）、房型偏好（下拉动态生成）、查询按钮；
- 校验：退房日期必须晚于入住日期，否则 Toast 报错；
- 查询成功后自动携带三个条件跳转「客房预订」页；
- **精选房型卡片**：封面（渐变底 + 房型 emoji + 房型名角标 + 库存胶囊）、设施标签、简介、单价与合计；
- 「查看全部房型 →」快捷入口。

### 3.2 客房预订（核心）

- **查询条件**：与首页一致，可独立重新查询；页头副标题实时显示「X 入住 · Y 退房 · 共 N 晚」；
- **房型卡片**：每张卡片展示——房型名、设施标签（床数/带窗/卫浴/WiFi 等）、简介、单价（¥xx /晚）、按当前日期折算的「共 N 晚 · 合计 ¥xx · 到店支付」、立即预订按钮；
- **实时可订量（库存口径）**：

```
房型可订数 = 该房型可售房数 − 与查询日期段重叠的「待到店」预订数
可售房数   = 该房型总房数 − 维修中 − 停用（与桌面端入住率口径一致）
重叠判定   ：预订.checkIn < 查询.checkOut 且 预订.checkOut > 查询.checkIn
剩余 > 0 →「剩余 N 间」角标，可预订
剩余 = 0 →「已订满」红色角标，按钮置灰禁用
```

- 库存为**房型级**：游客只看到「该房型还剩几间可订」，**不选择、也不看到具体房间号**；
- 正式版中可售房数应改为按日期段动态计算（覆盖在住/预定占房），v1 原型以「空闲房数 − 重叠待到店预订」近似。

### 3.3 在线预订流程（核心）

**预订弹窗**：

1. 顶部摘要卡：房型、入住/退房（N 晚）、单价、**预估房费**（单价 × 晚数）+ 「到店支付，另收押金」提示；
2. 表单字段与校验：

| 字段 | 必填 | 校验规则 |
|------|:---:|----------|
| 入住人姓名 | ✔ | 非空，≤20 字 |
| 手机号 | ✔ | `1` 开头 11 位数字 |
| 身份证号 | ✘ | 17 位数字 + 1 位数字/X |

3. 提交前二次校验房型可订量（防止并发下订满）。

**提交成功**：

- **库存扣减（不锁房）**：仅写入预订单（房型 ID + 入住/退房日期段 + 客人信息 + `PENDING`），**不指定具体房间、不变更任何房间状态**；库存因预订单的存在而自然减少；
- 生成预订号：`R + yyyyMMdd + 3 位序号`（序号按当日已有预订数 +1，不足 3 位补零）；
- 记住本次手机号，成功页可一键带出查询「我的预订」。

**预订成功页**：

- 大图标 + 「预订成功」；
- 高亮展示预订号（等宽字体、虚线边框强调）；
- 入住摘要：姓名 · **房型**（如「大床房 ×1」）· 日期区间 · 晚数 · 预估房费。**不展示房号**——房号到店办理入住时由前台分配；
- 到店提示：入住日 18:00 前到店，出示预订号或手机号，到店时从该房型空闲房中分配房间；修改/取消去「我的预订」；
- 双按钮：继续浏览 / 查看我的预订。

> 原型演示版成功页展示了具体房号（简化演示）；正式版按本节规则隐藏房号。

### 3.4 我的预订

- **查询**：输入预订手机号（11 位校验）→ 列出该手机号全部预订，按提交时间倒序；
- **列表列**：预订号（等宽高亮）、房型（×间数）、入住 → 退房日期、状态 Tag、操作；
  - 待到店单显示「大床房 ×1（房号到店分配）」；已转入住单显示实际分配的房号；
- **状态与可用操作**：

| 状态 | Tag 样式 | 游客可执行操作 |
|------|----------|----------------|
| 待到店 PENDING | 紫色圆点胶囊 | **取消预订** |
| 已转入住 CONVERTED | 蓝色圆点胶囊 | 无（到店已由前台分配房间并办理入住） |
| 已取消 CANCELLED | 灰色圆点胶囊 | 无 |

- **取消预订流程**：点击取消 → confirm 二次确认 → 预订标记 `CANCELLED` → **无需释放任何房间**（预订单未锁房），日期段库存自动回补 → Toast 反馈并刷新列表与房型卡片；
- 无记录时展示空态文案「该手机号暂无预订记录」。

## 四、核心业务流程

### 4.1 游客在线预订流程

```
首页/预订页选日期 → 查询房型（实时可订量）→ 点「立即预订」
  → 弹窗填写姓名/手机号/身份证 → 提交（库存二次校验）
  → 扣减房型库存（不锁房、不指定房号）→ 生成 R 预订号 → 成功页
```

### 4.2 预订 → 到店闭环（与桌面端联动）

```
游客预订（仅锁定房型库存，无房号）→ 桌面端预订单列表显示「待到店」
  → 客人到店 → 前台转入住：先从该房型空闲房中分配房间（系统推荐可改选）
  → 预订单回填房号 → 房态: 空闲→已入住 → 预定单标记已转入住
  → 入住/结算流程走桌面端既有逻辑
```

### 4.3 在线取消流程

```
我的预订 → 输入手机号查询 → 待到店单点「取消预订」→ 二次确认
  → 预订: 待到店→已取消 → 无需释放房间，日期段库存自动回补
```

### 4.4 房态联动边界

游客端**不直接变更任何房间状态**；预订仅体现为「房型日期段库存」的减少。入住、打扫、维修、停用、以及转入住时的选房与房态流转，全部由桌面端管理。

## 五、数据与展示规则

| 规则 | 说明 |
|------|------|
| 预订模型 | **只订房型，不订房号**：预订单记房型 + 日期段，房号到店转入住时由前台分配（见 1.2） |
| 预订号编码 | `R + yyyyMMdd + 3位序号`，与桌面端预定单规则一致 |
| 金额显示 | 统一 `¥xx`，合计 = 单价 × 晚数；晚数 = 退房日期 − 入住日期（天） |
| 日期校验 | 入住日期 ≥ 今天；退房日期 > 入住日期 |
| 库存口径 | 房型级可订数 = 可售房数 − 日期段重叠的待到店预订数（见 3.2） |
| 状态 Tag 色 | 待到店紫 / 已转入住蓝 / 已取消灰（沿用语义 Tag 规范） |
| 手机号 | 查询与预订的唯一游客凭证，不设密码 |

## 六、数据落库与扩展建议（对接 `民宿管理系统-数据库设计-v1.sql`）

### 6.1 直接复用的表

| 表 | 用途 |
|----|------|
| `room_type` | 房型卡片数据源（名称、基础定价） |
| `room` | 库存计算（`type_id` + `status`）；房号仅在转入住分配后回填到预订单 |
| `reservation` | 预订单落库（`res_no` / `guest_name` / `guest_phone` / `status`；`room_id` 预订时为空） |

### 6.2 需要扩展的点（建议 DB v1.1）

- **房型预订模型（本节核心）**：v1 的 `reservation.room_id` 为 `NOT NULL`，与「预订不指定房号」冲突。调整为：
  - `room_id` 改为 **NULL 允许**（预订时为 NULL，转入住分配房间后回填），保留外键；
  - **新增 `type_id INT UNSIGNED NOT NULL`**（预订锁定的房型 → `room_type.id`），库存归属与库存计算的主键；
  - **新增复合索引** `idx_type_dates (type_id, check_in_date, check_out_date)`，支撑房型级库存重叠查询；
- **日期段预订**：v1 的 `reservation` 表只有 `arrive_time`（预计到店时间），无入住/退房日期段。游客端按「入住日期 + 退房日期」预订，建议增加：
  - `check_in_date DATE NOT NULL`（入住日期）
  - `check_out_date DATE NOT NULL`（退房日期，> check_in_date）
- **渠道来源**：建议增加 `channel ENUM('WALK_IN','WEB') DEFAULT 'WALK_IN'`，区分前台代客与游客自助（`op_user_id` 在 Web 渠道为 NULL）；
- **转入住衔接**：桌面端「转入住」时需**先选房再办理**（在该房型空闲房中分配，系统可自动推荐），按 `check_out_date` 计算预计退房时间（而非固定次日 12:00），保证账期一致。

### 6.3 并发与一致性

- 提交预订需在事务中：**按房型 + 日期段做库存校验与预占**——对该房型相关行加锁（`SELECT ... FOR UPDATE`），重算「可售房数 − 重叠待到店预订数」，≥1 才写入预订单并提交，否则回滚提示已订满；
- 由于不锁具体房间，**不存在同房并发争抢**，争抢粒度是「房型 × 日期段」的库存余量；
- 桌面端转入住分配房间时，同样在事务内校验所选房间当日无重叠预订单/入住单后再置房态。

## 八、范围边界

**v1 包含**：首页营销与快速查询、客房预订（日期查询/实时可订量）、在线预订（表单校验/房型库存扣减/预订号/成功页）、我的预订（手机号查询/在线取消）、公共导航与响应式布局。

**v1 明确不做**：在线支付与退款、会员登录注册、改期/换房、房号在线自选、短信通知、OTA 对接、优惠券营销、发票开具、小程序端。

## 九、待确认事项（评审时拍板）

1. **到店保障规则**：入住日 18:00 前未到店且未联系前台 → 预订自动释放，是否需要系统自动执行（定时任务）还是前台手工处理？
2. **同一手机号预订上限**：是否限制单手机号同时待到店预订数（如 ≤3 间），防止恶意占房？

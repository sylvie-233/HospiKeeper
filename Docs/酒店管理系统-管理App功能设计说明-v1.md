## 一、系统概述

### 1.1 定位

面向**老板/管理员**的桌面端简化版移动 App（MAUI）。民宿老板经常不在店里，真实需求是"人不在店时也能盯店"——今天营收多少、入住率、有没有新预订、房间该打扫的扫了没，以及偶尔在外面做的两个轻决策（取消预定、调价）。

设计原则：**知情 + 轻决策**。

- **知情**：经营看板、房态、预订单、在住、日志全部只读呈现，数据与前台桌面端实时同源；
- **轻决策**：全 App 仅两个写操作——**取消预定**、**快捷改价**，风险可控、不需要复杂权限设计；
- **红线**：涉及钱和证件的操作（入住登记、退房结算、收款押金、证件登记）**一律留在前台桌面端**，App 内相关入口只做提示引导。

### 1.2 与另外两端的关系（三端一库）

| 事项 | 管理 App（老板版） | 桌面端（前台/管理员） | 游客 Web |
|------|------------------|---------------------|----------|
| 用户 | 老板/管理员（ADMIN） | 前台（FRONT）+ 管理员 | 游客（免登录） |
| 形态 | MAUI 手机 App | Avalonia 桌面系统 | Blazor Web 门户 |
| 房态变更 | **不产生**任何房态变更（只读） | 全部六种房态流转的唯一入口 | 不产生（只扣房型库存） |
| 写操作 | 取消预定、快捷改价 | 开房/退房/结算/改房态/档案维护 | 创建预订、在线取消 |
| 数据 | 共用同一个 MySQL，实时同步 | 同左 | 同左 |

### 1.3 形态与风格

- **手机 App 形态**：竖屏布局，底部 5 Tab 导航（看板/房态/预定/在住/我的），二级页带返回，弹层统一用底部抽屉（Bottom Sheet）；
- **视觉规范**：延续桌面端 Ant Design 色板与语义色，主色 `#2563eb`；房态卡片采用与桌面端**完全一致的饱和渐变全覆盖色 + 白字**（绿/蓝/紫/青/金/灰），三端同一套颜色语言；
- **演示形态**：原型内置演示数据（与桌面端/游客 Web 原型对齐：房间 101–208、房型 128/168/198、预订号 R 前缀、同一批客人与预订单）；正式版对接 MySQL。

## 三、功能模块详细设计

### 3.1 登录

- 复用 `sys_user` 表账号体系；**仅 `role='ADMIN'` 且 `status='ACTIVE'` 可登录**，FRONT 账号登录时明确拒绝并提示；
- 登录成功更新 `last_login` 并写 `op_log`（动作=登录）；
- 退出登录二次确认。

### 3.2 经营看板（默认首页）

**指标口径（与桌面端一致）**：

```
今日营收      = daily_revenue_stat(当日).revenue
较昨日涨跌    = 今日营收 − 昨日营收（涨红 ↑ / 跌绿 ↓ / 持平灰）
入住率        = 已入住房数 ÷ 可售房数（可售 = 总房数 − 维修 − 停用）
待到店        = reservation 中 status='PENDING' 的单数
押金占用      = Σ checkin_record(LIVING).deposit
待处理条目    = WEB 渠道待到店预订 + CLEANING 房间（待保洁确认）+ 今日预退（plan_out_time=今天且 LIVING）
```

**今日营收 Hero 卡**：大数字 + 涨跌胶囊，信息优先级最高；
**三列指标卡**：入住率（附 x/y 间）、待到店（附 WEB 渠道单数）、押金占用（附在住间数）；
**近 7 日营收柱状图**：取 `daily_revenue_stat` 近 7 条，今日柱高亮，柱顶标数值；
**待处理列表（折叠式）**：

- 默认显示前 3 条，超出折叠为「查看全部 N 条 ▾」展开条，展开后可收起，**保证看板首屏高度稳定**；
- 每条含色点（按类型）、标题、说明，**可点击跳转**：WEB 预订 → 预定管理、待保洁 → 房态页、今日预退 → 在住列表；
- 无待处理时展示空态「暂无待处理事项」；
- 「预定」Tab 红点角标 = 待处理条目数，为 0 时自动隐藏。

### 3.3 房态总览（只读）

- 双维度筛选：楼层（全部/1 层/2 层）× 房态（六态），胶囊筛选条；
- 房卡：3 列网格，全覆盖房态色 + 白字（与桌面端配色常量一致），显示房号/房型/房态/在住客人；
- 图例统计条：六种房态数量；
- 点击房卡 → 底部抽屉详情：楼层/标价、当前房态、在住客人（姓名/电话/入住→预退/押金/追加/经办前台）、预定客人；底部固定说明"管理端只读，房态操作回前台"。

### 3.4 预定管理（写操作一：取消预定）

- 分段筛选：全部 / 待到店 / 已转入住 / 已取消，对应 `reservation.status`（PENDING/CONVERTED/CANCELLED）；
- 卡片：预订号（等宽字体，点击开详情抽屉）、状态 Tag、客人姓名/电话、渠道 Tag（**游客在线 WEB / 前台代订 WALK_IN**）、房型/房号、到店时间；
- **WEB 渠道待到店单**：房号位置显示橙色「未分配」，呼应"房型预订、房号到店分配"模型（见游客 Web 设计说明 1.2）；
- 预定详情抽屉：预订号/客人/房型×晚数×单价/房号（未分配说明分配规则）/到店时间/渠道/状态；
- **取消预定**：仅 PENDING 单显示按钮 → confirm 二次确认（提示库存即时回补）→ 状态置 `CANCELLED` → 若已分配房号且房态为「预定」则回置「空闲」→ 写 `op_log` → Toast 反馈并刷新看板/房态/列表。

### 3.5 在住列表（只读）

- 头部：押金占用合计；卡片：房号/客人/房型/入住→预退/单价/押金/追加消费/经办前台；
- 页面入口的信息按钮点击提示"结算请回前台桌面端办理"，**不提供任何结算操作**。

### 3.6 我的（写操作二：快捷改价）

- 个人信息卡：头像、姓名、民宿名、ADMIN 胶囊标识、数据同步状态（绿点 + 最近同步时间）；
- **快捷改价**：底部抽屉列出 `room_type` 三房型当前定价 → 点「调价」弹输入 → 校验（正整数、不得与现价相同）→ 更新 `room_type.base_price` 并同步冗余 `room.price` → 写 `op_log` → Toast 确认；抽屉底部固定影响说明（即时同步前台标价与散客默认单价，在住订单不受影响）；
- **操作日志**（二级页）：按类型筛选（全部/预定/改价/登录），卡片展示动作/操作人/对象/明细/时间，数据源 `op_log`；
- 关于本应用：版本、功能边界说明（柜台业务回桌面端）；
- 退出登录。

## 四、核心业务流程

### 4.1 日常查看（主流程，纯只读）

```
登录 → 看板（营收/入住率/待到店/押金 + 待处理提醒）
  → 发现 WEB 新预订 → 待处理条目点击 → 预定管理查看详情
  → 房态页确认空房情况 → 结束（转入住由前台到店办理）
```

### 4.2 远程取消预定（写流程）

```
预定管理 → 待到店单 → 取消预定 → 二次确认
  → reservation.status = CANCELLED（房型日期段库存自动回补）
  → 若已分配房号且房态=预定 → 房态回置空闲
  → 写 op_log → 刷新看板/房态/列表 → Toast 反馈
```

### 4.3 远程调价（写流程）

```
我的 → 快捷改价 → 选房型 → 输入新价（校验）→ 确认
  → room_type.base_price 更新（同步 room.price 冗余）
  → 写 op_log → 前台桌面端即时生效 → Toast 反馈
```

### 4.4 与前台/游客 Web 的协同边界

- 游客 Web 新预订落库后，自动出现在 App 看板待处理与预定管理（WEB 渠道标签）；
- 前台桌面端开房/退房/打扫后，App 房态与看板随查询刷新同步；
- App 端所有写操作均写 `op_log`，前台可在桌面端日志中看到"管理端 App 操作"来源。

## 六、数据落库分析（对接 `民宿管理系统-数据库设计-v1.sql`）

### 6.1 结论：现有 9 张表可完整承载 v1 全部功能，**无需新增表**

| 表 | App 中的用途 |
|----|-------------|
| `sys_user` | 登录校验（role/status/last_login） |
| `room_type` | 看板/改价（base_price）、房卡房型名 |
| `room` | 房态总览、入住率、待保洁提醒（status） |
| `reservation` | 待到店统计、预定管理（status/channel/type_id/check_in_date/check_out_date 齐备，房型预订模型已落地） |
| `checkin_record` | 在住列表、押金占用、今日预退（plan_out_time） |
| `extra_charge` | 在住卡片的追加消费 |
| `checkout_bill` | （间接）营收数据来源之一，App 不直接展示 |
| `op_log` | 操作日志页、App 写操作留痕 |
| `daily_revenue_stat` | 今日营收/环比/近 7 日柱状图 |

### 6.2 曾评估、本期明确不做的点

- **消息通知中心**：需要新增 `notification` 表（含已读状态、类型、广播范围等字段）承载，且正式推送需接 MAUI 系统推送能力。本期按"不新增功能点"原则砍掉，待处理提醒由看板折叠列表 + Tab 角标承担。若二期要做，表结构与生成来源（预订落库/改价事件驱动 + 定时任务扫描保洁超时、18:00 未到店）已在本节评估过，可直接启用。

### 6.3 查询与同步

- App 为**查询驱动**（无本地持久化），每次进入页面/下拉刷新实时查询 MySQL，天然与桌面端同步；
- 同步状态条显示最近一次成功查询时间；
- 写操作（取消/改价）在事务内完成并同步刷新相关页面数据。

## 七、MAUI 实现映射建议

| 原型元素 | MAUI 实现 |
|----------|-----------|
| 技术形态 | **.NET MAUI + Blazor Hybrid**（Razor 组件跑在 BlazorWebView 中，可复用游客 Web 的组件与业务服务层）；数据访问 EF Core（Pomelo MySQL Provider） |
| 目标平台 | Android / iOS（手机包）；同一工程可扩展 Windows 桌面包 |
| 导航骨架 | `MauiProgram` + Shell（`AppShell.razor`）：TabBar 五项（看板/房态/预定/在住/我的）+ 日志二级页路由 |
| 登录 | `Login.razor` + `IAuthService`（校验 `sys_user`，会话内保存当前用户） |
| 看板 | `Dashboard.razor` + `KpiCard.razor`、`RevenueBarChart`（可用原生图表或轻量 SVG）；`IPendingService` 汇总三类待处理条目 |
| 房态 | `RoomBoard.razor` + `RoomCard.razor`（参数：房间、房态色映射常量类）；筛选状态用组件参数/级联值 |
| 抽屉 | `BottomSheet.razor` 通用组件（房间详情/预定详情/改价表单复用） |
| 业务服务 | `IRoomQueryService`（房态/入住率）、`IReservationService`（查询/取消，事务内）、`IPricingService`（改价，同步 room.price 冗余）、`IOpLogService`（写日志）——与游客 Web/桌面端共用同一服务层定义 |
| 数据刷新 | 进入页面查询 + 下拉刷新（`RefreshView`）；v1 不做实时推送 |
| 状态 Tag/色卡 | 与桌面端一致的常量映射类（`STATUS_COLOR` → CSS class / MAUI Color） |
| 安全 | ADMIN 角色服务端校验（接口层拒绝 FRONT）；App 端仅做 UI 引导 |

## 八、范围边界

**v1 包含**：登录（仅 ADMIN）、经营看板（指标/图表/折叠待处理）、房态总览（只读色卡 + 详情）、预定管理（筛选/详情/取消预定）、在住列表（只读）、我的（快捷改价/操作日志/关于/退出）、公共能力（Tab 导航/底部抽屉/Toast/空态）。

**v1 明确不做**：消息通知与系统推送（需新增 `notification` 表，二期评估）、入住登记、退房结算、收款押金、房态变更操作、客人/房间/房型档案维护、账号管理、报表导出、多门店、游客端功能（由游客 Web 承担）。

## 九、待确认事项（评审时拍板）

1. **数据刷新频率**：v1 用"进页查询 + 手动下拉刷新"即可满足，是否需要定时轮询（如 30s~1min 自动刷新看板）？
2. **取消预定的权限口径**：管理员取消前台代客的预定单是否需要限制（如仅 WEB 渠道单，或全部可取消）？
3. **改价幅度约束**：是否设置单次调价上下限（如 ±30%）或与 `room.min_price` 底价联动校验？
4. **消息通知二期**：若确认要做，`notification` 表结构本期是否预留进 DB 迁移脚本（只建表不接功能）？
5. **发版形态**：v1 先发 Android 包给老板自装，还是三平台（Android/iOS/Windows）同时出？
